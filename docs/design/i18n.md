# Internationalisation (i18n) Design

## Overview

`my-finance` targets Indian users whose preferred language may be English, Hindi, or one of the other major Indian languages. All user-visible text — labels, error messages, status strings, placeholders, alerts — must be sourced from language JSON files. No string literals may be hardcoded in components or API response bodies.

---

## Supported Locales

| Code | Language  | Status          |
|------|-----------|-----------------|
| `en` | English   | Default/fallback |
| `hi` | Hindi     | Shipped v1      |
| `ta` | Tamil     | Planned         |
| `te` | Telugu    | Planned         |
| `bn` | Bengali   | Planned         |
| `mr` | Marathi   | Planned         |

All locales share the same JSON key structure. Adding a new locale means adding a new file — no code changes required.

### Locale file structure

All locale files live under `apps/web/src/locales/`. Each language gets a directory; each feature area gets its own JSON namespace file.

```
apps/web/src/locales/
├── en/
│   ├── common.json        # navigation, buttons, generic status messages
│   ├── auth.json          # login, logout, registration, session errors
│   ├── overview.json      # dashboard / net-worth summary page
│   ├── cards.json         # credit cards feature
│   ├── accounts.json      # bank accounts feature
│   ├── loans.json         # loans feature
│   ├── investments.json   # investments feature
│   └── insurance.json     # insurance policies feature
└── hi/
    ├── common.json
    ├── auth.json
    ├── overview.json
    ├── cards.json
    ├── accounts.json
    ├── loans.json
    ├── investments.json
    └── insurance.json
```

### Key naming convention

- All keys are `camelCase`.
- Nested groups use dot notation in code (`t('errors.notFound')`) and nested objects in JSON.
- Error sub-keys mirror the backend `error.code` values in lowercase: `pan_invalid`, `rate_limit_exceeded`.

```json

  "pageTitle": "Credit Cards",
  "creditLimit": "Credit Limit",
```

### i18n singleton (`apps/web/src/i18n.ts`)

Import and bundle locale files at build time — no runtime HTTP fetch needed for v1.

```ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';

import enCommon from './locales/en/common.json';
import enAuth from './locales/en/auth.json';
import enOverview from './locales/en/overview.json';
import enCards from './locales/en/cards.json';
import enAccounts from './locales/en/accounts.json';
import enLoans from './locales/en/loans.json';
import enInvestments from './locales/en/investments.json';
import enInsurance from './locales/en/insurance.json';

import hiCommon from './locales/hi/common.json';
import hiAuth from './locales/hi/auth.json';
import hiOverview from './locales/hi/overview.json';
import hiCards from './locales/hi/cards.json';
import hiAccounts from './locales/hi/accounts.json';
import hiLoans from './locales/hi/loans.json';
import hiInvestments from './locales/hi/investments.json';
import hiInsurance from './locales/hi/insurance.json';

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    fallbackLng: 'en',
    supportedLngs: ['en', 'hi'],
    defaultNS: 'common',
    ns: ['common', 'auth', 'overview', 'cards', 'accounts', 'loans', 'investments', 'insurance'],
    resources: {
      en: {
        common: enCommon,
        auth: enAuth,
        overview: enOverview,
        cards: enCards,
        accounts: enAccounts,
        loans: enLoans,
        investments: enInvestments,
        insurance: enInsurance,
      },
      hi: {
        common: hiCommon,
        auth: hiAuth,
        overview: hiOverview,
        cards: hiCards,
        accounts: hiAccounts,
        loans: hiLoans,
        investments: hiInvestments,
        insurance: hiInsurance,
      },
    },
    interpolation: { escapeValue: false },
    detection: {
      order: ['localStorage', 'navigator'],
      caches: ['localStorage'],
      lookupLocalStorage: 'mf_lang',
    },
  });

export default i18n;
```

Import this singleton once in `main.tsx` before rendering:

```tsx
import './i18n';
import React from 'react';
import ReactDOM from 'react-dom/client';
import App from './App';

ReactDOM.createRoot(document.getElementById('root')!).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>,
);
```

### Component usage

```tsx
import { useTranslation } from 'react-i18next';

const CreditCardList: React.FC = () => {
  const { t } = useTranslation('cards');

  return (
    <>
      <Typography variant="h5">{t('pageTitle')}</Typography>
      <Typography variant="caption" color="text.secondary">
        {t('creditLimit')}
      </Typography>
    </>
  );
};
```

For strings that mix JSX elements, use the `Trans` component:

```tsx
import { Trans } from 'react-i18next';

// en/auth.json: { "termsNote": "By continuing you agree to our <1>Terms of Service</1>." }
<Trans i18nKey="auth:termsNote" components={[<span />, <Link href="/terms" />]} />
```

### Language switcher

A `LanguageSwitcher` component calls `i18n.changeLanguage(code)`. The chosen code is persisted to `localStorage` under key `mf_lang` automatically by the detector plugin.

```tsx
import { useTranslation } from 'react-i18next';
import { Select, MenuItem } from '@mui/material';

const LOCALES = [
  { code: 'en', label: 'English' },
  { code: 'hi', label: 'हिंदी' },
] as const;

const LanguageSwitcher: React.FC = () => {
  const { i18n } = useTranslation();

  return (
    <Select
      value={i18n.language}
      onChange={(e) => i18n.changeLanguage(e.target.value)}
      size="small"
    >
      {LOCALES.map(({ code, label }) => (
        <MenuItem key={code} value={code}>{label}</MenuItem>
      ))}
    </Select>
  );
};
```

### Number and date formatting

i18next handles string translations. Number and date formatting uses the native `Intl` API — do not pass formatted strings through the translation layer.

```tsx
// Currency — always INR, always en-IN grouping (₹5,00,000)
const formatINR = (amount: number): string =>
  new Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR' }).format(amount);

// Date — respects the active locale
const formatDate = (date: Date, locale: string): string =>
  new Intl.DateTimeFormat(locale === 'hi' ? 'hi-IN' : 'en-IN', {
    day: '2-digit', month: 'short', year: 'numeric',
  }).format(date);
```

## Backend i18n

### Purpose

The API returns `error.message` strings that surface directly in the UI. These must be translatable. All other backend internals (logs, audit records) remain in English.

### Library

```bash
npm install i18next i18next-fs-backend
```

| Package           | Role                                            |
|-------------------|-------------------------------------------------|
| `i18next`         | Core engine (same library, Node.js environment) |
| `i18next-fs-backend` | Loads JSON locale files from the filesystem  |

### Locale file structure

```
apps/api/src/locales/
├── en.json
└── hi.json
```

Each file is a flat namespace with two top-level groups: `error` (API error codes) and `validation` (Zod field-level messages).

```json
// en.json
{
  "error": {
    "pan_invalid": "PAN format is invalid",
    "pan_already_registered": "A PAN profile already exists for this account",
    "pan_not_found": "No PAN profile found for this account",
    "unauthorized": "Authentication required",
    "forbidden": "You do not have permission to perform this action",
    "not_found": "The requested resource was not found",
    "rate_limit_exceeded": "Too many requests. Please try again in a few minutes.",
    "internal": "An unexpected error occurred. Please try again."
  },
  "validation": {
    "pan_required": "PAN is required",
    "pan_format": "PAN must be 10 characters: 5 letters, 4 digits, 1 letter (e.g. ABCDE1234F)",
    "email_required": "Email address is required",
    "email_invalid": "Enter a valid email address",
    "password_min": "Password must be at least 8 characters",
    "password_required": "Password is required"
  }
}
```

### i18n singleton (`apps/api/src/i18n.ts`)

```ts
import path from 'path';
import i18next from 'i18next';
import Backend from 'i18next-fs-backend';

export const initI18n = async (): Promise<void> => {
  await i18next.use(Backend).init({
    fallbackLng: 'en',
    supportedLngs: ['en', 'hi'],
    backend: {
      loadPath: path.join(__dirname, 'locales/{{lng}}.json'),
    },
    interpolation: { escapeValue: false },
  });
};
```

Call `await initI18n()` in `app.ts` before starting the Express server.

### Language detection middleware

```ts
import type { Request, Response, NextFunction } from 'express';
import i18next from 'i18next';

declare module 'express-serve-static-core' {
  interface Request {
    language: string;
  }
}

export const localeMiddleware = (req: Request, _res: Response, next: NextFunction): void => {
  const raw = req.headers['accept-language'] ?? 'en';
  const requested = raw.split(',')[0]?.split('-')[0]?.toLowerCase() ?? 'en';
  req.language = i18next.options.supportedLngs?.includes(requested) ? requested : 'en';
  next();
};
```

Place `localeMiddleware` in the middleware chain immediately after `express.json()` and before route handlers.

### Translating error responses

```ts
import i18next from 'i18next';

// In a route handler or error middleware:
const message = i18next.t(`error.pan_invalid`, { lng: req.language });
res.status(400).json({ error: { code: 'PAN_INVALID', message } });
```

The `code` field remains a stable English constant (for frontend logic branching). The `message` field is the translated human-readable string.

### Zod validation error messages

Override default Zod messages at the schema level, sourcing strings from i18n:

```ts
const panSchema = (lng: string) =>
  z.string({
    required_error: i18next.t('validation.pan_required', { lng }),
  }).regex(/^[A-Z]{5}[0-9]{4}[A-Z]$/, i18next.t('validation.pan_format', { lng }));
```

Call this factory inside the route handler where `req.language` is available.

## Middleware order (with i18n)

```
helmet()
cors()
express.json()
localeMiddleware      ← new: sets req.language from Accept-Language
rateLimiter
auth.middleware
audit.middleware
route handlers
```

---

## Rules — always apply

1. **No hardcoded strings in components.** Every visible string comes from `t('key')`.
2. **No hardcoded strings in API responses.** Every `error.message` comes from `i18next.t('error.<code>', { lng })`.
3. **English is the fallback.** If a key is missing from a locale file, i18next falls back to `en` — never silently renders a key string.
4. **Key names are stable.** Renaming a key in a JSON file is a breaking change — treat it as a migration. Add the new key, keep the old one until all locales are updated, then remove the old one.
5. **Numeric and date formatting is NOT in JSON files.** Use `Intl.NumberFormat` / `Intl.DateTimeFormat` directly — do not put formatted strings like `₹5,00,000` into locale files.
6. **Currency is always INR.** The `en-IN` locale is the canonical grouping format for all locales (Indian users expect lakh/crore grouping regardless of their language preference).

## Testing

### Frontend

Wrap the component under test with the real i18n instance:

```ts
import { I18nextProvider } from 'react-i18next';
import i18n from '../../i18n';

const renderWithI18n = (ui: React.ReactElement) =>
  render(<I18nextProvider i18n={i18n}>{ui}</I18nextProvider>);
```

Assert on the translated English string (default locale in tests), not the key:

```ts
expect(screen.getByText('Credit Cards')).toBeInTheDocument();  // correct
expect(screen.getByText('cards.pageTitle')).toBeInTheDocument(); // wrong
```

### Backend

Pass `lng: 'en'` explicitly in unit tests so results are deterministic regardless of system locale:

```ts
const message = i18next.t('error.pan_invalid', { lng: 'en' });
expect(message).toBe('PAN format is invalid');
```
